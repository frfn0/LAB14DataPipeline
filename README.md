## Задание 1. Разработка сборщика данных на Go

### Что сделано

Сборщик на Go обходит два эндпоинта OpenWeatherMap — текущую погоду и
прогноз на пять дней с шагом три часа — и складывает результат в
JSON-файл, по одному объекту на строку.

Каждый город обрабатывается отдельной горутиной, готовые записи передаются
в канал, отдельная горутина пишет их в файл. Число городов,
обрабатываемых одновременно, ограничивается параметром `-concurrency`.

Ответы двух эндпоинтов приводятся к одному типу `WeatherRecord`: структуры
у них разные, а конвейер на Python должен работать с однородной таблицей.
Время наблюдения переводится в часовой пояс города, а не сервера: между
Якутском и Москвой девять часов, и без перевода все города выглядели бы как
одно и то же время суток.

Города по умолчанию: Москва, Санкт-Петербург, Новосибирск, Екатеринбург,
Казань, Нижний Новгород, Краснодар, Владивосток, Сочи, Якутск. Они
разнесены по часовым поясам и климату, иначе сравнение средних температур
объяснялось бы временем суток, а не погодой.

### Запуск

```powershell
$env:OWM_API_KEY = "<ключ>"

go run ./cmd/collector -log "logs\collector.log"

# другой параллелизм
go run ./cmd/collector -concurrency 3

# другой список городов и файл
go run ./cmd/collector -cities "Москва,Казань" -out "data/raw/two.jsonl"
```

В транспорте клиента выключены keep-alive соединения. На этой машине

## Задание 2. Добавление буферизации и пакетной записи

### Что сделано

Между сбором и записью стоит канал с буфером, а записи пишутся пачками.
Пачка записывается одной операцией, когда выполняется любое из двух условий:
набралось `-batch-size` записей или прошёл `-flush-interval`. Таймер нужен
для редкого потока — иначе накопленное ждало бы конца сбора.

Между накопителем и файлом нет промежуточного буфера намеренно: такой буфер
сам объединял бы записи в блоки, и разница между режимами была бы незаметна.
Одна операция записи здесь — это одна операция записи в файл.

Собираются счётчики: число принятых записей, операций записи, объём в
байтах, средний и наибольший размер пачки, сколько пачек записано по
размеру, по таймеру и при завершении.

### Запуск

```powershell
$env:OWM_API_KEY = "<ключ>"

# режим по умолчанию: пачка 50, дописывание каждые 250 мс
go run ./cmd/collector -log "logs\collector.log"

# режим без пакетной записи: одна операция на запись
go run ./cmd/collector -batch-size 1 -flush-interval 0

# крупная пачка
go run ./cmd/collector -batch-size 100
```

| Параметр | Назначение | По умолчанию |
|----------|------------|--------------|
| `-batch-size` | сколько записей накапливать перед записью; 1 отключает буферизацию | 50 |
| `-flush-interval` | дописывание по таймеру; 0 отключает | 250 мс |
| `-channel-buffer` | ёмкость канала между сбором и записью | 256 |

### Фактический вывод

```
msg="запись завершена" records=410 write_ops=410 bytes=225000 avg_batch=1.0  max_batch=1   flush_by_size=410 flush_by_time=0 flush_on_close=0
msg="запись завершена" records=410 write_ops=10  bytes=225000 avg_batch=41.0 max_batch=50  flush_by_size=8   flush_by_time=1 flush_on_close=1
msg="запись завершена" records=410 write_ops=6   bytes=225000 avg_batch=68.3 max_batch=100 flush_by_size=3   flush_by_time=2 flush_on_close=1
```

| Размер пачки | Операций записи | Сокращение | Средняя пачка |
|---------------|-----------------|------------|---------------|
| 1 (без буферизации) | 410 | - | 1.0 |
| 50 | 10 | в 41 раз | 41.0 |
| 100 | 6 | в 68 раз | 68.3 |

Объём записанных данных одинаков во всех случаях: 225000 байт. Содержимое
файлов совпадает — побайтовое различие только во времени сбора, оно
разное в каждом прогоне:

```

```

Общее время сбора почти не изменилось (745 мс против 838 мс): сбор упирается
в сеть, а не в запись — двадцать сетевых запросов против 225 КБ данных.
Сокращение числа операций записи при этом то же самое и не зависит от
источника: оно проявится при плотном потоке записей.

## Задание 3. Реализация graceful shutdown

### Что сделано

Сборщик обрабатывает SIGINT и SIGTERM. Остановка двухступенчатая:

- **Первый сигнал** — новые города не запускаются, а уже начатые
  дорабатывают: текущие данные не теряются, а оставшиеся города просто не
  начинаются.
- **Повторный сигнал или истечение `-grace`** — запросы и отправка записей
  прерываются.

После сбора печатается отчёт: сколько городов собрано, сколько провалено,
сколько пропущено. Буфер записи дописывается по закрытию канала, поэтому
неполная пачка не теряется и не ждёт, пока наберётся следующая.

Обычная и аварийная остановка разведены намеренно. В первой версии цикл
отправки записей содержал `select` между отправкой в канал и закрытым
каналом остановки: оба готовы, выбор случайный, и часть записей текущего
города просто не доходила до файла.

На Windows от операционной системы приходит только Ctrl+C, то есть
os.Interrupt; SIGTERM там не поддерживается, но подписка на него оставлена,
чтобы тот же код работал в Linux без правок.

### Запуск

```powershell
$env:OWM_API_KEY = "<ключ>"

# обычная работа
go run ./cmd/collector -log "logs\collector.log"

# остановка по Ctrl+C: текущие города дорабатывают, остальные пропускаются
go run ./cmd/collector

# ждать дорабатывания дольше или меньше
go run ./cmd/collector -grace 30s
```

| Параметр | Назначение | По умолчанию |
|----------|------------|--------------|
| `-grace` | сколько ждать дорабатывания текущих городов после сигнала | 10 с |

### Фактический вывод

Лог при остановке во время сбора двенадцати городов:

```
msg="получен сигнал остановки, дорабатываю текущие данные" signal=interrupt grace=10s
msg="сбор остановлен" interrupted=true completed=2 failed=0 skipped=8 records=82
msg="запись завершена" records=82 write_ops=2 bytes=44900 avg_batch=41.0 max_batch=50 flush_by_size=0 flush_by_time=1 flush_on_close=1
msg="сбор завершён" cities=10 elapsed_ms=1815 output=data/raw/weather.jsonl grace=10s
```

Два города успели собраться по 41 записи, восемь не начались, и все 82 записи
оказались в файле.

### Как проверяется остановка

На Windows другому процессу нельзя отправить Ctrl+C из скрипта, а жёсткое
завершение не даёт коду отработать. Поэтому проверка разбита на две части:

- обработка сигналов — тесты с подставленным каналом сигналов: первый
  сигнал, повторный сигнал, истечение времени ожидания;
- весь путь остановки — интеграционный тест: сбор городов, пакетная запись,
  закрытие канала, содержимое файла и дописанный буфер.

Тесты проверяют главное: начатый город дорабатывает, не начатые
пропускаются, неполная пачка дописывается, при аварийной остановке ничего не
зависает.

## Задание 4. Импорт данных в Python (Polars)

### Что сделано

Собранные JSON-файлы загружаются в таблицу Polars. Скрипт показывает первые
пять строк, типы полей, количество строк и пропуски, а также общие сведения:
число файлов, городов, эндпоинтов, размер в памяти и период наблюдений.

Схема полей задана явно в `pipeline/common.py` и передаётся в `read_ndjson`:
вывод типов по первым строкам файла превращает целочисленный счётчик в
дробный из-за одного пустого значения, а изменение контракта сборщиком должно
останавливать конвейер, а не менять типы посреди него.

Отдельно проверяется состав полей первой записи. Polars при чтении с готовой
схемой отсутствующее поле молча заполняет пустыми значениями, и расхождение
контракта прошло бы незаметно, а данные появились бы в отчёте как пропуски.

Первые пять строк выводятся обычным текстом: при двадцати семи полях таблица
шире экрана, и встроенный вывод Polars обрезал середину.

## Задание 5. Очистка и валидация данных

### Что сделано

Семь шагов очистки, каждый считает, сколько строк изменил, и печатает это в
отчёте.

| № | Шаг | Что делает |
|---|-----|-----------|
| 1 | Полные дубликаты | Удаляет совпадающие целиком строки |
| 2 | Повторные наблюдения | Оставляет по одной записи на наблюдение, самую свежую |
| 3 | Разбор времени | Добавляет `observed_utc`, `observed_local`, `collected_utc`, `local_date` |
| 4 | Обработка пропусков | Удаляет строки без обязательных полей, остальные пропуски заполняет |
| 5 | Проверка диапазонов | Удаляет строки с явно неправдоподобными значениями |
| 6 | Приведение типов | Приводит поля к схеме очищенных данных |
| 7 | Сортировка | Упорядочивает по городу и моменту наблюдения |

**Пропуски.** Строки без города, момента наблюдения или температуры
удаляются: такую запись нельзя ни сгруппировать, ни показать на графике.
Остальные пропуски заполняются: числовые поля нулём, текстовые — пустой
строкой. Для осадков, порывов и облачности нулевое значение означает то же
самое, что и отсутствие сообщения.

**Время.** У городов разные часовые пояса, от +03:00 до +10:00, поэтому
время хранится в трёх полях: `observed_utc` для временного ряда,
`observed_local` и `local_date` для суточных агрегатов. Без разделения
наблюдение в полночь по местному времени попало бы в предыдущие сутки UTC.

**Диапазоны.** Границы шире наблюдавшихся значений: температура от −80 до
+60, давление от 850 до 1100 гПа, влажность и облачность от 0 до 100.
Задача — поймать явную нелепость, а не отсечь редкие, но настоящие погодные
условия.

### Запуск

```powershell
python -m pipeline.clean_data
```

Чтобы шаг удаления повторов работал на настоящих данных, сборщик запускался
дважды в разные файлы: повторный сбор — обычная ситуация, и без него

## Задание 6. Агрегационный анализ

### Что сделано

Пять группировок, каждая отвечает на свой вопрос. Методичка требует одну
группировку по ключевому полю, но по одному полю погоду не опишешь: сумма
осадков за пять дней и суточная динамика температуры — разные вопросы.

| № | Группировка | Что показывает |
|---|-------------|----------------|
| 1 | по городу | какая погода стоит в городе за весь период |
| 2 | по городу и местной дате | как погода менялась по дням |
| 3 | по типу погоды | сколько наблюдений пришлось на каждый тип |
| 4 | по эндпоинту | чем наблюдение сейчас отличается от прогноза |
| 5 | ранжирование городов | кто где по температуре и влажности |

**Сумма приводится не везде.** Сложение температур в градусах не значит

количество наблюдений. Для температуры, влажности, давления, ветра и
облачности приведены среднее, минимум и максимум.

**Группировка по дням идёт по местной дате**, а не по дате в UTC: сутки в
городе заканчиваются в полночь по его времени, и наблюдение в 00:30 по Москве

## Задание 7. Сохранение в Parquet

### Что сделано

Очищенные данные записываются в `reports/weather.parquet` одним файлом со

**Проверка round-trip.** После записи файл читается обратно и сравнивается с
исходной таблицей построчно: количество строк и столбцов, состав полей, типы,
значения, порядок столбцов. Тихая запись может потерять строки, сменить тип
целого на дробное или обрезать текст, и это обнаружилось бы только в задании
8, когда данные уже ушли дальше по конвейеру.

**Сравнение четырёх способов сжатия**, потому что выбор сжатия влияет на размер
файла, а DuckDB в задании 8 читает именно этот файл.

## Задание 8. Анализ через DuckDB

### Что сделано

SQL-запрос к `reports/weather.parquet` из задания 7 содержит всё требуемое:
фильтрацию в `WHERE`, группировку в `GROUP BY`, отбор групп в `HAVING`,
сортировку в `ORDER BY` и пять агрегатов.

```sql
SELECT
    city AS город, count(*) AS наблюдений,
    min(temp_c) AS мин, avg(temp_c) AS средняя, max(temp_c) AS макс,
    sum(snow_mm + rain_mm) AS осадки
FROM read_parquet('reports/weather.parquet')
WHERE temp_c < 10 AND (rain_mm > 0 OR snow_mm > 0)
GROUP BY city
HAVING count(*) > 0
ORDER BY мин
```

**Результаты сверены построчно.** Если бы значения разошлись, замер времени
ничего не значил бы, потому что считалось разное.

**Сравнение сделано в двух частях**, потому что в первой версии оно было
нечестным:

| Что сравнивается | DuckDB | Polars |
|------------------|--------|--------|
| Чтение Parquet | 16.69 мс | 1.19 мс |
| Вычисление запроса, данные в памяти | 2.27 мс | 0.93 мс |
| Полный цикл | 16.44 мс | 2.11 мс |

В первой версии Polars считал по таблице в памяти, а DuckDB каждый раз
перечитывал файл — и разница в 23 раза давало чтение, а не запрос.

**Каждый вариант выполняется пять раз, сравнивается медиана.** Единственный
замер на Windows скачет из-за планировщика ОС: первые замеры Polars стабильно
были втрое медленнее следующих.

**Победитель не объявляется**, пока разница не проходит два порога: больше
1 мс и больше 20 %.

