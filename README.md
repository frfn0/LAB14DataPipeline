## Задание 1. Разработка сборщика данных на Go

### Что сделано

Сборщик на Go обходит два эндпоинта OpenWeatherMap — текущую погоду и
прогноз на пять дней с шагом три часа — и складывает результат в
JSON-файл, по одному объекту на строку.

Каждый город обрабатывается отдельной горутиной, готовые записи передаются
в канал, отдельная горутина пишет их в файл. Число городов,
обрабатываемых одновременно, ограничивается параметром `-concurrency`.

Ответы двух эндпоинтов приводятся к одному типу `WeatherRecord`: структуры
у них разные, а конвейер на Python должен работать с однородной таблицей.
Время наблюдения переводится в часовой пояс города, а не сервера: между
Якутском и Москвой девять часов, и без перевода все города выглядели бы как
одно и то же время суток.

Города по умолчанию: Москва, Санкт-Петербург, Новосибирск, Екатеринбург,
Казань, Нижний Новгород, Краснодар, Владивосток, Сочи, Якутск. Они
разнесены по часовым поясам и климату, иначе сравнение средних температур
объяснялось бы временем суток, а не погодой.

### Запуск

```powershell
$env:OWM_API_KEY = "<ключ>"

go run ./cmd/collector -log "logs\collector.log"

# другой параллелизм
go run ./cmd/collector -concurrency 3

# другой список городов и файл
go run ./cmd/collector -cities "Москва,Казань" -out "data/raw/two.jsonl"
```

```

time=2026-10-07T21:48:34.582+03:00 level=INFO msg="город собран" city=Якутск records=41 elapsed_ms=1532
time=2026-10-07T21:48:36.109+03:00 level=INFO msg="записей записано" count=410
```

Ключ API в логи не пишется — только маска `50b2...8eaa`.

### Параллельный сбор

Один и тот же набор городов, отличается параллелизм:

| Параллелизм | Время сбора |
|-------------|-------------|
| 1 | 15.09 с |
| 5 | 3.08 с |

Выигрыш в 4.9 раза. Время на город выросло с 1.5 до 1.55 с: источник
ограничивает скорость, поэтому пять одновременных запросов идут с той же
скоростью, что и один, а ожидающих городов в пять раз меньше.

### Про отключённые постоянные соединения

В транспорте клиента выключены keep-alive соединения. На этой машине
переиспользуемое соединение с OpenWeatherMap возвращало заголовки ответа и
не отдавало тело: у запроса прогноза код 200 и ноль байт, зависание ровно до
таймаута. Малая текущая погода по тому же соединению проходила. Отдельная
проверка это показала:

```
keep-alive включён   попытка 1: текущая 200  488 байт 0.71 с | прогноз 200      0 байт 20.00 с
keep-alive выключен  попытка 1: текущая 200  488 байт 0.64 с | прогноз 200 17050 байт  0.85 с
```

Цена решения — новое TCP-соединение на запрос. Для двух запросов на город
это несущественно: полный прогон занимает 3 секунды.
