Задание 10: документирование конвейера: фактический вывод
=========================================================

Дата проверки: 2026-10-07
Инструменты: Python 3.10.6, Polars 2.0.0, duckdb 1.5.6, matplotlib 3.6.2,
plotly 7.1.0, pytest 9.0.3, ruff, Go 1.x

Требование методички
--------------------

"Подготовить README с описанием: архитектура конвейера (схема
«Go-сборщик → JSON → Polars → Parquet → DuckDB → визуализация»), инструкция по
запуску, примеры запросов и графиков."

Что сделано
-----------

1. **Схема архитектуры** в Mermaid: семь шагов, стрелки между ними и файлы на
   каждом шаге. Показано, что DuckDB читает Parquet, а графики — очищенный
   JSON, и оба получают данные из задания 5.

2. **Таблица «что читает, что записывает, сколько строк»** на каждом шаге:

   | Шаг | Что читает | Что записывает | Строк |
   |-----|-----------|----------------|-------|
   | 1-3 сборщик | OpenWeatherMap API | `data/raw/weather.jsonl` | 410 |
   | 4 импорт | `data/raw/*.jsonl` | — | 820 |
   | 5 очистка | `data/raw/*.jsonl` | `data/interim/weather_clean.json` | 420 |
   | 6 агрегаты | `data/interim/weather_clean.json` | — | 420 |
   | 7 Parquet | `data/interim/weather_clean.json` | `reports/weather.parquet` | 420 |
   | 8 DuckDB | `reports/weather.parquet` | — | 5 |
   | 9 графики | `data/interim/weather_clean.json` | `reports/charts/` | — |

   Без неё слова «конвейер» и «Parquet» ничего не говорят о размерах. Не видно,
   что 410 строк на выходе сборщика превращаются в 820 на импорте и в 420
   после очистки, и не видно почему так.

3. **Описание формата данных**: JSON Lines, пример строки, состав полей.
   Отдельно объяснено, почему не массив: дозапись работает без переписывания
   файла, и частично записанный файл остаётся читаемым.

4. **Время в четырёх полях** описано как решение, а не как перечисление: у
   городов часовые пояса от +03:00 до +10:00, и один момент наблюдения — это
   четыре разных значения.

5. **Таблица всех десяти флагов сборщика** с значениями по умолчанию.
   Двух флагов не хватало: `-timeout` и `-env-key` использовались, но не были
   описаны.

6. **`scripts/run_all.ps1`** — запуск заданий 4-9 подряд с проверками
   качества кода. Скрипт останавливается на первом шаге с ненулевым кодом
   возврата: после очистки с ошибкой запускать Parquet и графики бессмысленно,
   и доводить конвейер до конца на неполных данных опаснее, чем остановиться
   и показать, где сломалось.

7. **Примеры запросов** — три запроса с фактическим выводом, и один из них
   показан и как вызов из Python.

8. **Таблица графиков** со ссылками на файлы.

9. **24 теста документации**: README, PROMPT_LOG и скрипт запуска.

Примеры запросов с фактическим выводом
--------------------------------------

Запрос из задания 8:

```sql
SELECT city AS город, count(*) AS наблюдений,
       min(temp_c) AS мин, avg(temp_c) AS средняя, max(temp_c) AS макс,
       sum(snow_mm + rain_mm) AS осадки
FROM read_parquet('reports/weather.parquet')
WHERE temp_c < 10 AND (rain_mm > 0 OR snow_mm > 0)
GROUP BY city
HAVING count(*) > 0
ORDER BY мин;
```

```
город            наблюдений   мин °C   средняя °C  макс °C  осадки мм
Якутск                    6    -4.73        -3.58    -2.72       1.64
Новосибирск              15     2.33         5.41     8.29       6.84
Екатеринбург              2     7.31         7.55     7.80       0.53
Санкт-Петербург           6     8.84         9.38     9.92       7.23
Москва                    2     9.58         9.63     9.69       0.30
```

Три самых тёплых города:

```sql
SELECT city, round(avg(temp_c), 2) AS средняя, count(*) AS наблюдений
FROM read_parquet('reports/weather.parquet')
GROUP BY city
ORDER BY средняя DESC
LIMIT 3;
```

```

Краснодар     16.18           42
Сочи          15.50           42
Владивосток   14.85           42
```

Погода по дням в Якутске:

```sql
SELECT local_date, count(*) AS наблюдений, round(avg(temp_c), 1) AS средняя
FROM read_parquet('reports/weather.parquet')
WHERE city = 'Якутск'
GROUP BY local_date
ORDER BY local_date;
```


Последняя строка — единственный день с двумя наблюдениями: прогноз на 13-е
октября заканчивается в 18:00 по местному времени, а до этого прогноза не

Что показали тесты
------------------

24 теста документации. Проверяется то, что иначе расходится с кодом тихо.

- все локальные ссылки из README ведут в существующие файлы;
- для каждого задания 4-9 есть команда запуска, и соответствующий модуль
  есть в репозитории;
- флаги сборщика в README совпадают с флагами в исходнике `config.go`;
- таблица заданий не содержит незавершённых пунктов;
- заглушек «будет дополнено» не осталось ни в README, ни в PROMPT_LOG;
- PROMPT_LOG заполнен по всем десяти заданиям, в каждом разделе есть промпт и
  результат;
- неудачные попытки описаны таблицей с колонкой «Как исправлено»;
- ключ API не встречается ни в README, ни в PROMPT_LOG;
- скрипт запуска записан с BOM и разбирается без синтаксических ошибок;
- скрипт вызывает все шесть шагов и проверяет код возврата после каждого;
- описаны все семь шагов конвейера, есть диаграмма и формат данных;
- приведены настоящие размеры данных: 410 строк от сборщика и 420 после
  очистки.

Тесты документации нашли четыре расхождения, которые иначе остались бы
незамеченными: не хватало двух флагов в таблице, раздел задания 10 ещё
существовал только заглушкой, а в PROMPT_LOG не было формулировки, которую
ожидал тест.

Найденные при проверке дефекты
------------------------------

1. **Скрипт не запускался.** PowerShell 5.1 читает `.ps1` без BOM как ANSI,
   и кириллические имена `Задание`, `Команда`, `Аргументы` в ключах хешей
   превращались в мусор: разборщик падал с
   `ParserError: The hash literal was incomplete`. Файл перезаписан в UTF-8 с
   BOM, а все имена переменных и ключи хешей переведены на латиницу — так
   скрипт не зависит от кодировки чтения.

2. **Тест документации не импортировался.** Команда PowerShell
   `$errors | ForEach-Object { $_.Message }` была собрана f-строкой Python, и
   её фигурные скобки считались подстановкой:
   `SyntaxError: f-string: invalid syntax`. Команда склеивается из строк, путь
   подставляется конкатенацией.

3. **Тест «все десяти заданий выполнены» ловил чужие строки.** Регулярное
   выражение искало таблицу по всему README и находило `50` и `100` в других
   таблицах — например, в таблице флагов. Теперь берётся только таблица
   заданий: по заголовку и до первой пустой строки.

4. **Тест требовал формулировки, которой в логе нет.** Он ждал раздел
   «Найденные при проверке дефекты», а дефекты описаны таблицей «Неудачные
   попытки». Тест переписан на проверку самой таблицы и наличия колонки
   «Как исправлено».

5. **Порог числа проверок кода возврата был взят с запасом.** Тест требовал
   семь вхождений `LASTEXITCODE`, а в скрипте их шесть — по числу шагов.
   Порог теперь считается от числа шагов в тесте, а не задаётся константой,
   значение которой расходится с реальностью.

6. **Два флага не были описаны:** `-timeout` и `-env-key`. Тест на флаги,
   читающий их из исходника, это нашёл бы сразу, если бы был написан раньше.
   Добавлена таблица всех десяти флагов с значениями по умолчанию.
