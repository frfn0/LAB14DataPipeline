Задание 1. Разработка сборщика данных на Go: фактический вывод
===========================================================

Дата проверки: 2026-10-07
Источник данных: OpenWeatherMap API, ключ из переменной окружения
OWM_API_KEY
Инструменты: Go 1.26.1

Требование методички
--------------------

"Реализовать на Go программу, которая собирает данные из источника,
указанного в варианте. Использовать горутины для параллельного сбора (если
применимо). Данные должны сохраняться в JSON-файлы (каждый объект на
отдельной строке)."

Предметная область варианта 2: анализ погодных данных, источник —
OpenWeatherMap API.

Что сделано
-----------

1. Клиент источника, internal/owm.

   Собираются два эндпоинта:

   - `/data/2.5/weather` — текущая погода, одно наблюдение на город;
   - `/data/2.5/forecast` — прогноз на пять дней с шагом три часа,
     40 точек на город.

   Ответы приводятся к одному типу WeatherRecord: два разных эндпоинта
   отдают разные структуры, а конвейер на Python должен работать с
   однородной таблицей.

   Время наблюдения переводится в часовой пояс города, а не сервера. Разница
   для Якутска и Москвы — девять часов, и без перевода все города в отчёте
   выглядели бы как одно и то же время суток.

2. Сборщик, cmd/collector.

   На каждый город запускается своя горутина. Готовые записи передаются в
   канал, отдельная горутина пишет их в файл по одной строке на запись.

   Число одновременно обрабатываемых городов ограничивается параметром
   `-concurrency` (по умолчанию 5): без ограничения десять городов создали бы
   десять одновременных соединений с источником.

   Ошибка одного города не останавливает сбор остальных: иначе одна
   опечатка в названии обнуляла бы весь прогон.

3. Настройки, internal/config.

   Города, путь вывода, параллелизм, таймаут и путь к логу задаются флагами,
   ключ API — переменной окружения. Ключ в логи не пишется: в запись о
   старте попадает только его маска `50b2...8eaa`.

   По умолчанию собираются десять городов России: Москва, Санкт-Петербург,
   Новосибирск, Екатеринбург, Казань, Нижний Новгород, Краснодар,
   Владивосток, Сочи, Якутск. Города разнесены по часовым поясам и климату:
   иначе сравнение средних температур объяснялось бы временем суток, а не
   погодой.

4. Тесты: 21 тест стандартным пакетом testing.

   - `internal/owm/client_test.go` (11): разбор обоих эндпоинтов, перевод
     времени в часовой пояс города, ошибка источника с кодом 401, пустой
     ответ, битый JSON, ответ без блока погоды, отмена по контексту,
     соответствие имён JSON-полей тем, что читает Python;
   - `internal/config/config_test.go` (8): значения по умолчанию, разбор
     флагов, обязательность ключа, отказ на неверных значениях, чтение ключа
     из своей переменной, маскирование ключа;
   - дополнительно проверяется, что при недоступном прогнозе наблюдение
     текущей погоды не выбрасывается.

Запуск
------

  $env:OWM_API_KEY = "<ключ>"
  go run ./cmd/collector -log "logs\collector.log"

  # другой параллелизм или другой список городов
  go run ./cmd/collector -concurrency 3 -cities "Москва,Казань"

Параллельный сбор даёт выигрыш в 4.9 раза
-------------------------------------------

Один и тот же набор городов, отличается только параллелизм:

  > go run ./cmd/collector -concurrency 1
  msg="сбор завершён" cities=10 elapsed_ms=15092

  > go run ./cmd/collector -concurrency 5
  msg="сбор завершён" cities=10 elapsed_ms=3076

  последовательно 15.09 с, параллельно 3.08 с

Время на город при параллелизме 5 выросло с 1.5 до 1.55 с: источник
ограничивает скорость, поэтому пять одновременных запросов идут по той же
скорости, что и один, а ожидающих городов в пять раз меньше.

Проблема, найденная при первом запуске
---------------------------------------

Первый запуск собрал ноль записей за 41 секунду:

  msg="город не собран" city=Москва error="не удалось прочитать ответ
  https://api.openweathermap.org/data/2.5/forecast: context deadline exceeded"

curl при этом отвечал за 1.1 с и отдавал полный ответ 17 КБ. Проверка на
четырёх вариантах транспорта показала, что дело не в протоколе и не в
адресе: IPv4 и HTTP/1.1 работали так же хорошо, как вариант по умолчанию.
Отдельная проверка пары запросов на одном клиенте дала ответ:

  keep-alive включён   попытка 1: текущая 200 488 байт 0.71 с | прогноз 200      0 байт 20.00 с
  keep-alive включён   попытка 2: текущая 200 488 байт 0.64 с | прогноз 200      0 байт 20.00 с
  keep-alive включён   попытка 3: текущая 200 488 байт 0.66 с | прогноз 200      0 байт  2.99 с
  keep-alive выключен  попытка 1: текущая 200 488 байт 0.64 с | прогноз 200 17050 байт 0.85 с
  keep-alive выключен  попытка 2: текущая 200 488 байт 0.65 с | прогноз 200 17050 байт 0.86 с
  keep-alive выключен  попытка 3: текущая 200 488 байт 0.64 с | прогноз 200 17050 байт 0.85 с

На переиспользуемом соединении заголовки ответа приходят, а тело большого
ответа не приходит никогда: заголовок 200 есть, байтов 0, время ровно по
таймауту. Малая текущая погода по тому же соединению проходит. С
`DisableKeepAlives` каждый запрос идёт по своему соединению, и все ответы
приходят целиком.

Решение: постоянные соединения выключены в транспорте клиента. Цена — новое
TCP-соединение на каждый запрос, что для двух запросов на город
несущественно: полный прогон занимает 3 секунды.

Нестабильный тест, найденный при многократном прогоне
-----------------------------------------------

Первый прогон `go test ./...` на свежем клоне упал, хотя в рабочей копии всё
проходило. Многократный прогон (12 запусков) сузил причину до одного места:

  --- FAIL: TestCurrentWeatherMapsFields (0.00s)
      client_test.go:104: время запроса не измерено

Тест требовал `elapsed > 0`, то есть что измеренная длительность запроса
положительна. Тестовый сервер отвечает за микросекунды, и на Windows такая
длительность округляется до нуля: ровно один прогон из двенадцати это
поймал. Проверка заменена на осмысленную: измеренное время должно попасть в
поле `request_ms` собранной записи.

Заодно ускорен пакет тестов с 2.6 с до 0.7 с: в тесте отмены запроса
обработчик ждал 2 с и продолжал работать после падения теста, из-за чего
закрытие тестового сервера зависало. Теперь обработчик ждёт отмены запроса.

  > go test ./... -count=1   # 20 запусков подряд
  неудачных прогонов из 20: 0

Проверка гонок (`go test -race`) в этой системе недоступна: требуется
CGO, а компилятор gcc не установлен.
