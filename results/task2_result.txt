Задание 2. Добавление буферизации и пакетной записи: фактический вывод
===================================================================

Дата проверки: 2026-10-07
Инструменты: Go 1.26.1, OpenWeatherMap API

Требование методички
--------------------

"Модифицировать сборщик: добавить канал с буфером, реализовать пакетную
запись (накопить N записей или ожидать T секунд перед записью в файл).
Цель - снизить количество операций ввода-вывода."

Что сделано
-----------

1. Канал с буфером между сбором и записью.

   Ёмкость канала задаётся параметром `-channel-buffer` (по умолчанию 256).
   Раньше канал был на 16 записей: при десяти городах, отдающих по 41
   записе, сборщик постоянно упирался в запись и ждал её.

2. Пакетная запись, internal/writer.

   Записи накапливаются и пишутся одной операцией, когда выполняется любое
   из двух условий:

   - набралось `-batch-size` записей (по умолчанию 50);
   - прошёл `-flush-interval` (по умолчанию 250 мс).

   Таймер нужен для редкого потока: если записи приходят медленнее, чем
   размер пачки, накопленное не ждало бы конца сбора.

   Между накопителем и файлом намеренно нет промежуточного буфера: такой
   буфер сам объединял бы записи в блоки по 256 КБ, и разница между режимами
   стала бы незаметной. Одна операция записи здесь - это одна операция
   записи в файл.

3. Счётчики записи.

   Собираются: число принятых записей, число операций записи, объём в
   байтах, средний и наибольший размер пачки, сколько пачек записано по
   размеру, по таймеру и при завершении. По ним и оценивается эффект.

4. Режим сравнения.

   `-batch-size 1` отключает пакетную запись: это тот же сборщик, но с
   одной операцией записи на запись. На нём измеряется, сколько операций
   было до буферизации.

Запуск
------

  $env:OWM_API_KEY = "<ключ>"

  # режим по умолчанию: пачка 50, запись по таймеру каждые 250 мс
  go run ./cmd/collector -log "logs\collector.log"

  # режим без пакетной записи для сравнения
  go run ./cmd/collector -batch-size 1 -flush-interval 0

  # крупная пачка
  go run ./cmd/collector -batch-size 100

Результаты прогона
------------------

Один и тот же набор городов, отличаются только параметры записи.

  > go run ./cmd/collector -batch-size 1 -flush-interval 0
  msg="запись завершена" records=410 write_ops=410 bytes=225000 avg_batch=1.0  max_batch=1   flush_by_size=410 flush_by_time=0 flush_on_close=0

  > go run ./cmd/collector -batch-size 50 -flush-interval 250ms
  msg="запись завершена" records=410 write_ops=10  bytes=225000 avg_batch=41.0 max_batch=50  flush_by_size=8   flush_by_time=1 flush_on_close=1

  > go run ./cmd/collector -batch-size 100 -flush-interval 250ms
  msg="запись завершена" records=410 write_ops=6   bytes=225000 avg_batch=68.3 max_batch=100 flush_by_size=3   flush_by_time=2 flush_on_close=1

Сводка:

| Размер пачки | Операций записи | Сокращение | Средняя пачка |
|---------------|-----------------|------------|---------------|
| 1 (без буферизации) | 410 | - | 1.0 |
| 50 | 10 | в 41 раз | 41.0 |
| 100 | 6 | в 68 раз | 68.3 |

Объём записанных данных одинаков во всех трёх случаях: 225000 байт.

Содержимое файлов тоже совпадает. Побайтовое сравнение различается только
времем сбора: каждый прогон выполняется в свою секунду, поэтому `collected_at`
и `request_ms` отличаются. После исключения этих двух полей наборы записей
полностью идентичны:

  > python сравнить три файла без collected_at и request_ms
  записей в каждом: 410 410 410
  содержимое совпадает без времени сбора и времени запроса: True

Про время выполнения
-------------------

  пачка 1   собрано за 745 мс, запись завершена за 410 операций
  пачка 50  собрано за 838 мс, запись завершена за 10 операций

Общее время почти не изменилось, и это ожидаемо: сбор упирается в сеть, а не
в запись. За 410 записей файловой системе нужно 225 КБ, это ничто по
сравнению с двадцатью сетевыми запросами. Выигрыш буферизации проявляется
там, где записи идут плотным потоком: при росте числа городов или при
сборе с локального источника. Сокращение числа операций записи при этом
остаётся тем же - оно не зависит от источника.

Что показали тесты
------------------

1. Пачка пишется по достижении размера: 410 записей при пачке 50 дают девять
   операций записи - восемь полных пачек и остаток десять записей.

2. Режим без буферизации: 100 записей при пачке 1 дают ровно 100 операций
   записи.

3. Содержимое не меняется от буферизации: файлы, записанные по одной записи
   и пачками, содержат одни и те же строки.

4. Запись по таймеру срабатывает, когда пачка не набирается: при пачке в
   1000 записей и интервале 50 мс накопленное дописывается, не дожидаясь
   конца сбора.

5. При отмене накопленное не теряется: две записи, уже лежащие в канале,
   дописываются при остановке.

6. На каждый объект приходится ровно одна строка, строки читаются обратно в
   структуру записи.

Всего 30 тестов: 21 из задания 1 и 9 новых на пакетную запись.

Найденные при проверке дефекты
------------------------------

1. Первая версия писателя считала операции записи внутри буфера `bufio`.
   Тест показал ноль записанных строк: буфер не отдавал данные в файл до
   сброса, поэтому измерить эффект буферизации было нечем. Кроме того, сам
   буфер объединял бы записи, и разница между режимами была бы незаметна.
   Промежуточный буфер убран, теперь операция записи - это операция записи
   в файл.

2. При остановке терялись записи, уже лежащие в канале: при отмене готовы
   и канал, и сигнал, и `select` выбирал ветку произвольно - иногда канал,
   иногда сигнал. Тест ловил это через раз. Теперь при отмене сначала
   забирается всё, что уже положили в канал, и только потом дописывается
   накопленное. Это понадобится и в задании 3.

3. Ошибка записи пачки молча терялась: `flush` игнорировал результат
   `Write`. Сбор при этом продолжался, а данные не доходили до файла. Ошибка
   теперь запоминается и возвращается через `Err`, и сборщик завершается с
   ней.
